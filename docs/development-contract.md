# SALU 개발 계약

코드 구조와 화면 흐름, 권한·저장·검증에 적용하는 공통 규칙입니다.

## 구조

- React·TypeScript·Vite, Java 17·Spring Boot·MyBatis·MySQL. 의존성 버전은 Maven Wrapper·pom.xml·npm lockfile 기준

- Controller: 입력 검증·응답 DTO
- Service: 업무 규칙·소유권·참여자·트랜잭션
- Mapper: SQL
- `SecurityConfig`: URL 인증·역할·CSRF·세션·Security filter 오류
- `GlobalExceptionHandler`: MVC 공통 오류

- 기능별 패키지에 controller/service/mapper/DTO 배치
- DB 객체를 그대로 공개하지 않음
- 빈 기능 클래스를 미리 만들지 않음
- 기존 Salon에서 로직을 참고해도 초기 SQL·환경 값·DB·전체 업무 코드를 복사하지 않음

## 기존 Salon 참고

Salon(Spring 5·JSP)의 기능을 가져올 때 아래 방식은 따라 하지 않음

| Salon에서 보인 방식 | SALU 기준 |
|---|---|
| Controller마다 세션·역할 검사, CSRF 꺼짐, 기본 전체 허용 | URL 규칙은 `SecurityConfig` 한 곳, 기본 로그인 필요, CSRF 전체 적용. 소유권은 Service |
| Controller가 Mapper 직접 호출, 한 Controller에 여러 기능 | Controller → Service → Mapper. 기능별 패키지 |
| 공통 오류 처리 없음, 화면마다 다른 오류 | `ApiError` JSON 하나 |
| DB transaction 안에서 STOMP 전송 | commit 뒤 전송. 실패하면 화면이 API로 다시 불러옴 |
| 알림 생성이 여러 Service에 흩어지고 이동 주소를 문자열로 저장 | 알림은 종류와 대상 ID만 저장. 문구와 이동 화면은 화면 쪽 한 곳에서 정함 |
| 좋아요·신고 수를 반응 표와 별도 컬럼으로 증감 | 반응·신고 표에서 집계. 별도 숫자 컬럼을 두지 않음 |
| 사진을 `image_url`, `image_url2`처럼 컬럼으로 늘림 | 사진은 별도 표 |
| schema 파일을 손으로 맞춤, DB 접속 정보 Git 포함 | Flyway 새 번호 migration, 비밀 값은 `.env` |

## 화면과 자료

- 화면 목록·이동·뒤로 링크·메뉴별 화면 보관은 [화면 흐름](screen-flow.md)
- 실제 개인 자료와 `/examples/*`의 메모리 예시를 분리. 예시 자료를 기기에 영구 보관하거나 계정에 올리지 않음
- 예시 여부는 상단 띠에서만 표시하고 본문은 실제 서비스 문구·동선을 씀. 실제 디자이너 목록이 비어 있으면 예시 체험 진입을 제공하고, 가상 프로필·후기·기록은 실제 등록 자료와 구분. 예시 디자이너 지우의 사진·소개·후기와 커트 3건(9월 1일·7월 12일·5월 3일)은 확정한 예시 자료라 임의로 바꾸지 않음
- 예시 상담은 별도 메모리 저장소. 보내기는 실제와 같은 검사와 완료 화면을 거침(중복 클릭은 1건, 첨부는 보낸 때의 복사본, 실패 시 입력 유지)
- 예시에서 보낸 상담에는 몇 초 뒤 그 예시 디자이너의 정해진 예시 답변이 달려 `답변 대기` → `답변 도착`을 보여 줌. 다른 화면에 가 있어도 체험 중이면 달리고, 서버·알림은 거치지 않음. 예시에는 대화·후기가 없고, 체험 종료·초기화 때 상담과 답변을 함께 지움(10-24 결정, 구현 전)
- 실제 공간에서는 자동 답변을 만들지 않음. 같은 상담 화면을 서버([상담 API 계약](consultation-api.md))에 연결하고, 상담 하나를 대화방으로 써서 디자이너의 첫 메시지를 답변으로 봄. 개인 암호화 백업 저장을 상담 전달로 보지 않음
- 실제 상담 요청·답변은 로그인 필수. 디자이너·매장 조회와 예시 체험의 상담 화면은 로그인 없이 가능
- 개인 커트 준비와 상담은 별도 메뉴·상태. 기록에서 담당 디자이너 프로필로 들어간 상담은 그 디자이너에게 받은 커트만 첨부. 준비 내용에서는 프로필을 거치지 않고 바로 상담을 쓰고, 담당이 아닌 디자이너에게도 그 준비 내용을 첨부해 보냄(커트를 다시 고르지 않음)
- 상담 완료는 공통 완료 화면의 `○○ 디자이너에게 전달했어요`. 준비 완료 문구(`커트 준비를 마쳤어요`)를 상담 완료에 쓰지 않음
- 작성 화면은 한 작업에 집중. 커트 준비는 자료 선택 → 요청 작성 → 저장 전 확인 → 저장 완료 → 준비 내용. 확인 화면에 들어온 것만으로 저장하지 않음
- 커트·경과 생성/수정과 준비 저장은 기기 commit 성공 뒤 공통 완료 화면. 실패 시 입력 유지. 다른 메뉴로 옮긴 동안 완료돼도 지금 화면을 강제로 바꾸지 않음
- 터치 기기는 방향과 관계없이 하단 메뉴, 데스크톱은 상단 고정. 다크 모드·동작 줄이기·키보드 초점 지원
- 날짜 선택은 앱 달력·직접 입력 지원. 커트일은 오늘 이하, 경과일은 커트일 이상·오늘 이하. 기존 경과일 뒤로 커트 날짜 이동 금지. 업무 날짜는 Asia/Seoul 기준
- 시술·부위·필수 관찰 내용 검증. 전체 선택은 전체 해제와 대칭, 가격 증감은 천원 단위·직접 입력은 정수 원 단위
- 사진 JPEG/PNG/WebP, 장당 5 MiB 이하·작성 화면당 최대 6장. 실제 디코딩 검사. 처리 중 저장/중복 조작 방지, 확대 후 초점 복귀. 사진·없음·불러오기 실패 상태를 동일한 프레임으로 표시
- 개인 준비는 첨부 없이 가능. 상담(예시 포함)은 대상과 직접 고른 자료가 필요. 메모·경과·사진은 처음에 고르지 않은 상태이고 자동으로 첨부하지 않음
- 저장한 준비는 그때의 문장·날짜·사진을 유지하고, 원본 기록을 고쳐도 바뀌지 않음. 최신 기록을 쓰려면 직접 다시 고름. 준비 자체는 `준비 고치기`로 고칠 수 있음([개인 저장 계약](personal-storage.md))

## 공개 미용실·디자이너

- 공개 조회: `GET /api/salons`, `GET /api/designers`, `GET /api/designers/{id}`
- 미용실 등록: 인증·CSRF 필요한 `POST /api/salons`
- 본인 프로필: `GET/POST/PUT /api/my/designer-profile`. principal 소유자 기준, 프로필 없음은 GET 204, 생성은 201. 회원당 프로필 하나
- 가입만으로 디자이너 목록에 표시하지 않음. ACTIVE 계정의 공개 프로필만 목록/상세에 노출. 프로필 공개와 실제 디자이너 검증/상담 권한을 혼동하지 않음
- 미용실·담당자는 DB 선택, 이전 기록 재사용, 직접 입력 가능. 자유 입력 이름만으로 실제 프로필 자동 연결 금지
- 기록 당시 이름·매장 스냅샷과 현재 공개 프로필/소속 분리. 비공개·목록 장애가 과거 기록 읽기/작성 보존을 막지 않음
- 공개 디렉터리와 개인 암호화 백업을 분리. 상담 전송·답변은 디렉터리 API와 별도인 상담 API. 후기·찜·소속 이력은 [디자이너 API](designer-api.md). 후기는 디자이너 개인 프로필에 붙어 소속을 바꿔도 유지

## 오류와 권한

- 공통 오류는 `ApiError(code, message)`. Security와 MVC의 형식 일치
- Controller별 try-catch·redirect·새 오류 형식 금지

| 상태 | 처리 |
|---|---|
| 잘못된 입력/JSON | 400 / INVALID_REQUEST |
| 인증 필요 | 401 / AUTHENTICATION_REQUIRED |
| 권한/CSRF | 403 / ACCESS_DENIED 또는 CSRF_INVALID |
| 대상/경로 없음 | 404 / RESOURCE_NOT_FOUND |
| 방식 불일치 | 405 / METHOD_NOT_ALLOWED, Allow header 유지 |
| 업무 충돌/중복 | 409 / RESOURCE_CONFLICT |
| 크기/형식 | 413 / UPLOAD_TOO_LARGE, 415 / UNSUPPORTED_MEDIA_TYPE |
| 예상 밖 오류 | 500 / INTERNAL_ERROR, 고정 문구 |

- 원문 입력·비밀번호·SQL·내부 예외를 응답/로그에 넣지 않음
- 의도한 업무 오류만 명시적으로 변환
- 예외를 모두 400이나 성공 응답으로 바꾸지 않음

- 서버 개인 자료는 principal 소유자 기준
- 요청 role/memberId로 권한 부여 금지
- 디자이너 또는 매장 소속만으로 다른 사용자의 기록 접근 허용 금지
- 상담의 상세·사진·메시지·후기는 Service의 참여자 검사 필요
- 관리자 기능은 `/api/admin/**`에만 두고 SecurityConfig에서 ADMIN만 허용. 역할은 `members.role`, 지정은 DB에서만
- 공개 사진은 원본의 private URL을 재사용하지 않음

## 트랜잭션과 데이터 보존

- 다중 DB 변경은 Service의 Spring `@Transactional`, 조회 전용은 필요 시 `readOnly=true`. checked exception 롤백은 `rollbackFor` 명시
- Spring proxy 경유 호출. 조건부 UPDATE 0행·중복 key도 실패, 예외를 삼켜 부분 저장 금지
- 파일·HTTP·STOMP는 DB rollback으로 복구되지 않음. 해당 기능 구현 전 커밋 후 전송·실패 재처리/정리 정책 확정
- 실시간 신호는 `RealtimePublisher`로만 보냄. commit 뒤에 나가고, 신호에는 종류와 ID만 담아 화면이 API로 다시 불러옴. 놓친 신호는 다시 보내지 않음([알림 API](notification-api.md))
- 알림은 `NotificationService.create`로만 만듦. 업무 transaction 안에서만 호출됨(`MANDATORY`). 종류와 대상 ID만 저장하고 문구·이동 화면은 화면이 정함
- 적용된 Flyway migration 수정·삭제 금지, 변경은 새 migration. 기존 DB·volume·암호화 키 초기화 금지
- 앱 교체/복구 전 DB·환경·키 보관, 이전 앱과 현재 schema 호환성 확인. 이미지 태그만 되돌렸다고 DB까지 복구된 것으로 판단하지 않음

## 인증·저장·검증

- [인증 계약](login.md), [개인 저장 계약](personal-storage.md) 적용
- 서버 API는 [상담](consultation-api.md)·[알림](notification-api.md)·[디자이너](designer-api.md)·[커뮤니티](community-api.md) 계약 적용. 경로·필드·오류를 바꿀 때는 계약 문서를 먼저 고침
- 기기 저장과 계정 백업은 도메인 커트 CRUD/상담 전송 완료의 근거가 아님
- 새 가입·외부 소셜 동의/콜백은 별도 실제 검증 필요

- 공유 소스의 기본 확인: 프론트엔드 빌드·형식 검사, 백엔드 jar 빌드
- 실제 동작 확인: 로컬 검증 환경에서 화면·기기 저장·실제 인증·계정 백업·소유권·DB 커밋/롤백을 구분
- 테스트·fixture·Playwright·검증 도구는 로컬 전용, 운영 jar에 포함 금지
- 테스트 자체의 자동 트랜잭션 롤백으로 Service의 실제 커밋 여부를 가리지 않음
- 업무 DB·사용자 자료로 검증 금지, 테스트 전용 DB와 임시 계정 사용
- 비밀번호·CSRF token·세션 cookie가 담긴 trace·영상·스크린샷을 남기지 않음
- 검증 도구가 공유 소스에 없다는 이유로 검증하지 않은 기능을 완료 처리하지 않음
- 변경한 공통 동작은 해당 API·DB·브라우저에서 확인
