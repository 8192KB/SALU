# SALU 7주차 발표 흐름 검토와 개조식안

이전 검토안. 아래는 10/10 구현 상태에 대한 기록이며, 현재 저장 상태와 발표 범위는 [10/11 재검토](7주차_지난주예고기준_재검토.md) 우선 적용. 기존 PPTX/PDF는 수정 전 초안.

검토일: 2026-10-11. 구현·검증 기준은 2026-10-10 결과. 발표 시간 5분 이내, 개발 진행 상황 중심. 본문 4장으로 약 3~4분 설명 후 질문 대응 권장.

## 발표 방향

**6주차 예고 → 이번 주 구현 결과 → 개발 중 보완 → 남은 작업** 순서 권장. 2~6주차에서 설명한 서비스 필요성·벤치마킹·전체 기능은 이번 본문에서 반복하지 않음. 같은 커트의 기록·경과를 필요한 자료로 선택해 다음 요청을 만드는 흐름을 유지하고, 실제 디자이너 상담은 후속으로 표시.

기존 7주차 예시안은 새로운 기기 보관 방향을 설명하기에는 적절하지만, 현재 진행 보고에는 설계 제안의 비중이 큼. 현재 결과를 중심으로 별도 [개조식 진행보고 PPTX](SALU_7주차_발표_진행보고_개조식안.pptx)와 [본문 확인 PDF](SALU_7주차_발표_진행보고_개조식안.pdf) 구성. 기존 예시안은 장기 방향 검토용으로 보존.

캡스톤 폴더 루트의 실제 주차별 발표 파일 기준. PPTX의 `show=0` 슬라이드는 본 발표 비교에서 제외하고 보충 자료로만 확인. 6주차 루트 발표본과 `수정용/SALU_6주차_최종본.pptx`는 파일 SHA256 동일. 준비 폴더의 수정본·README는 이전 검토 이력이므로 실제 발표 흐름과 구분.

| 주차 | 본문 표시 / 파일 전체 | 발표 흐름 | 이번에 가져올 점 |
|---|---|---|---|
| 2 | 5 / 15 | 피드백 → 보완안 → 예약 중 사례 확인 → 개발 범위 → Q&A | 지난 발표에서 받은 요구와 이번 결과의 연결 |

| 4 | 6 / 7 | 지난 커트의 불편 → 기록 서비스 비교 → 부위별 요청 선택 → 카드 흐름 → 범위·Q&A | 구체적인 커트 사례를 사용한 설명 |

슬라이드 수는 숨김을 제외한 표시 수이며, 실제 발표한 장수나 발표 시간을 확인한 결과는 아님.

### 기존 7주차 흐름의 좋은 점

- 6주차의 기획 목업에서 실제 React 조작 화면으로 발전
- 실제 Spring 인증과 임시 기록의 차이를 표시
- 구현 결과·새 설계·검증 목표를 구분
- 8주차 시험과 발표 없음 반영

### 부족한 부분과 달라진 점

1. **지난주 예고와의 비교 부족**
   - 6주차 마지막 장의 저장·조회, React 화면, 기록 유지·권한 검증에 대한 결과표 부재
   - “무엇을 구현했고 무엇이 남았는가”를 첫 장에 제시할 필요
2. **새 기획 설명의 비중 증가**
   - 기존 7 예시안의 3·4·5장은 첫 진입·기기 저장·백업과 미래 검증 목표 중심
   - 개발 진행 보고에서는 실제 구현과 개선에 시간을 우선 배분
3. **개인 기록에서 상담으로 이어지는 중심이 약해질 가능성**
   - 6주차 2장의 “개인기록에 너무 가깝다” 피드백에 이어 혼자 사용·기기 보관이 다시 주제가 됨
   - 개인 사용은 진입 방식으로 설명하고, 고른 기록으로 다음 요청을 만드는 목적 유지
   - 실제 상담 전송·답변은 미구현이라고 명시
4. **개발 중 발견한 문제와 개선 과정 부족**
   - 가상 기록이 먼저 나오는 첫 화면, 기능 나열, 다음 행동의 강조 부족 등 실제 보완 내용이 빠짐
   - 문제 → 개선 → 확인한 결과의 세 줄 구조 권장
5. **현재 구현과 맞지 않는 설명**
   - 기존 3장의 새 첫 화면은 이제 소개 홈으로 구현됨
   - 둘러보기는 현재 별도 예시 체험이며 커뮤니티 열람이 아님
   - 기존 4·5장의 재접속 보관·로그아웃 후 유지·파일 복원은 여전히 목표
   - 현재 개인 기록은 새로고침·인증 전환 시 소실
6. **발표 문체의 차이**
   - 2~6주차의 짧은 기능명·명사형 항목에 비해 기존 7주차는 완성 문장 제목과 긴 부연 설명이 많음
   - 본문은 개조식, 이유·근거·한계는 짧은 발표자 노트로 분리

서비스 조사와 전체 일정의 비중을 줄이는 것은 이번 목적에 맞는 차이. 새 벤치마킹이나 전체 기능 소개를 늘릴 필요는 없음.

## 본문 4장: 그대로 옮길 개조식 문구

### 1. 이번 주 개발 진행 상황

- 6주차 예고: 계정·권한 / 커트·경과 저장·조회 / React 화면
- 현재 결과: 실제 인증 연결 / 기록·경과 입력·수정 / 홈·기록·준비 화면
- 남은 부분: 기록 영구 저장 / 계정별 기록 권한

발표 설명, 약 35~45초:

“지난주에는 계정과 기록 저장, React 화면을 연결하겠다고 말씀드렸습니다. 현재는 실제 로그인과 기록·경과 입력, 다음 커트 준비 화면까지 연결했습니다. 다만 기록은 메모리에만 보관돼서 재접속 후 유지와 계정별 기록 권한은 아직 남아 있습니다.”

### 2. 구현한 사용 흐름

- 소개 홈 → 커트 기록 시작
- 커트·경과 → 날짜별 입력·수정
- 참고 자료 선택 → 필요한 내용 선택
- 요청 작성·내용 확인 → 다음 커트 준비
- 경과는 선택 / 커트 준비는 3단계

실제 React 캡처 4개 사용. 사진·문구·날짜는 발표용 가상 자료이며 업무 DB 저장 결과가 아님.

발표 설명, 약 60~80초:

“이번에는 목업을 보여주는 단계에서 실제 입력하고 이동하는 단계로 넘어갔습니다. 커트한 날의 기록에 경과를 추가하고, 필요한 내용만 골라 다음 커트 요청을 정리할 수 있습니다. 경과는 꼭 작성할 필요가 없고, 준비 과정은 자료 선택·요청 작성·내용 확인 순서입니다. 여기까지는 준비본이며 실제 디자이너에게 전송되지는 않습니다.”

### 3. 개발 중 보완한 부분

- 첫 화면: 가상 기록 우선 → 소개 홈·개인 기록·예시 분리
- 화면 순서: 기능 나열 → 다음 행동 강조·3단계 준비
- 입력 동작: 지역 형식 날짜·즉시 펼침 → 연·월·일 표시·선택 정보 전환
- 확인 결과: PC·모바일 화면 54개 / 실제 인증 11개 통과

발표 설명, 약 45~60초:

“흐름을 확인하면서 처음 사용하는 사람이 무엇부터 해야 하는지 모호한 부분을 발견했습니다. 그래서 설명 홈을 만들고 개인 기록과 예시를 나눴습니다. 기록 상세에는 다음 커트 준비를 강조하고, 날짜 표시와 선택 정보의 펼침 동작도 정리했습니다. PC·모바일 화면 흐름과 실제 서버 로그인을 나눠 검증했습니다.”

### 4. 남은 작업과 다음 순서

- 기록 보존: 저장 범위 확정 → 커트·경과 저장·재조회
- 계정별 기록: 서버 소유권 연결 → 타인 접근 검증
- 실제 상담: 프로필·선택 자료 전송 → 두 계정 질문·답변
- 8주차: 시험 / 발표 없음

발표 설명, 약 35~45초:

“다음은 저장 범위를 확정하고 실제 기록을 저장·조회하는 부분을 연결할 예정입니다. 기록 유지와 다른 계정의 접근 차단을 확인한 뒤 실제 디자이너 상담을 이어 붙이겠습니다. 기기 보관과 서버 백업의 범위는 그 전에 정리해야 합니다. 8주차는 시험으로 발표가 없어, 이후 일정은 남은 작업량을 보고 조정하겠습니다.”

위 개발 순서는 후속 제안이며 이번에 구현하거나 완료 시점을 약속한 내용이 아님.

예상 질문:

- **저장이 된 것인가?** 이번 접속의 메모리만 사용. 영구 보관·재접속 유지 미연결.
- **6주차의 타인 접근 차단은?** 인증 연결과 임시 상태 초기화까지 확인. 기록 DB 소유권 검증은 후속.

- **혼자 기록하는 서비스로 바뀐 것인가?** 진입 부담을 줄인 것이며, 고른 기록을 다음 요청과 상담에 활용하는 목적 유지.
- **시험 주간에도 기능 완료를 약속하는가?** 8주차 발표 없음만 반영. 추가 기능의 납기 확정 없음.
